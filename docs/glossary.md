# Glossary — every term in SentinelOps

Each entry says what the thing is, then **where it is in our project**. If you can say the
bold part out loud, you can answer the question.

Read [how-it-runs.md](how-it-runs.md) alongside this; that one explains how the pieces fit
together, this one explains what each piece is called and why.

---

## 1. Containers and Kubernetes

**Container** — a program plus everything it needs to run (libraries, config), sealed in a box
so it behaves the same on any machine.
*Ours: order-service, payment-service, postgres and prometheus each run in one.*

**Image** — the frozen recipe a container is started from. `order-service:v2` is an image; a
running copy of it is a container.
*Ours: built with `docker build`, then imported into Kubernetes' own image store — Docker
Desktop keeps a separate one, which is why a plain `docker build` isn't enough.*

**Docker** — the tool that builds images and runs containers.

**Kubernetes (k8s)** — the manager that sits above Docker. You **declare** what you want ("two
copies of order-service") and it makes reality match, restarting anything that dies. You never
tell it *how*, only *what*.
*Ours: runs inside Docker Desktop on the laptop.*

**Pod** — one running copy of a workload; the smallest thing Kubernetes schedules. Pods are
disposable and get a new IP address every time they restart.
*Ours: 6 pods — 2 order-service, 2 payment-service, 1 postgres, 1 prometheus.*

**Deployment** — the object that says "keep N pods of this image running". It replaces dead
pods and handles rolling out a new version.
*Ours: `services/k8s/order-service.yaml` and friends.*

**Service** (Kubernetes Service) — a **stable name and port** that routes to whichever pods are
alive. Because pod IPs change, nothing ever connects to an IP.
*Ours: order-service connects to host `postgres`, port `5432`. **This is what our first demo
fault attacks** — the simulator moves that port to 5433 and every new connection times out.*

**ClusterIP / LoadBalancer / NodePort** — the three kinds of Service. ClusterIP is reachable
only inside the cluster; LoadBalancer is exposed outside.
*Ours: postgres is ClusterIP, prometheus is LoadBalancer — which is why `localhost:9090` works
with no port-forward.*

**Namespace** — a folder that separates groups of objects, and a security boundary.
*Ours: everything is in `default`; our agent identity cannot see any other namespace.*

**kubectl** — the command-line remote control for Kubernetes.
*Ours: `kubectl get pods`, `kubectl get svc postgres -o yaml`.*

**Manifest** — a YAML file declaring what you want to exist.
*Ours: everything in `services/k8s/`.*

**Rolling update vs Recreate** — two strategies for replacing pods. Rolling starts new ones
before killing old ones (no downtime); Recreate kills everything first.
*Ours: postgres uses **Recreate**, deliberately, so two Postgres processes never share one data
directory and corrupt it.*

**Readiness probe** — a check Kubernetes runs to decide whether a pod is ready for traffic.
*Ours: postgres runs `pg_isready`.*

**Replica** — one of the N copies. "Scaling" means changing N.
*Ours: `scale_service` is one of the four actions the AI is allowed to propose, limited to 1–5.*

**ServiceAccount** — an identity for a **program** (as opposed to a person) to authenticate to
the Kubernetes API.
*Ours: `sentinelops-agent`. This is our outer safety fence.*

**RBAC (Role-Based Access Control)** — the permission system. A **Role** lists allowed verbs
(get, list, patch…) on resources; a **RoleBinding** attaches that Role to an identity.
*Ours: `services/k8s/sentinelops-rbac.yaml`. We can read pods/logs/deployments and patch
deployments and services. **We cannot delete anything, create anything, or read secrets.**
Provable live with `kubectl auth can-i delete deployments`.*

**kubeconfig** — the file holding credentials for talking to a cluster.
*Ours: `sentinelops-agent.kubeconfig`, generated by a script, gitignored.*

**managedFields** — Kubernetes records **which client last wrote each field**, with a timestamp.
*Ours: our writes are labelled `sentinelops-agent`, the simulator's `sentinelops-simulator`. This
is how we prove from **outside** our own app that the AI made the change.*

## 2. Metrics and observability

**Observability** — being able to tell what's happening inside a system from the signals it
emits, without attaching a debugger.

**Prometheus** — the metrics database. It **pulls**: every 5 seconds it visits each pod's
`/metrics` URL and stores what it finds, with timestamps.
*Ours: one pod, UI at `localhost:9090`.*

**Scraping** — the act of Prometheus fetching `/metrics`. Pods opt in with annotations
(`prometheus.io/scrape: "true"`).

**Pull vs push** — Prometheus asks the services (pull) rather than services sending to it
(push). Pull means a dead service is visibly absent rather than silently quiet, and nothing
needs to know Prometheus' address.
*Same reason we poll Freshservice for approvals instead of using webhooks: the laptop only ever
makes outbound calls.*

**Counter / Gauge / Histogram** — the three metric shapes. A counter only goes up (total
requests). A gauge goes up and down (connections in use). A histogram records a distribution
(how long requests took).
*Ours: `order_requests_total` counter, `db_pool_waiting` gauge, `order_request_duration_ms`
histogram.*

**PromQL** — Prometheus' query language.
*Ours, the detector's actual query:*
```promql
sum(rate(order_errors_total[30s])) / sum(rate(order_requests_total[30s]))
```

**rate()** — converts a counter into a per-second rate over a window. `[30s]` is the window.

**histogram_quantile()** — pulls a percentile out of a histogram.
*Ours: p95 latency on the incident charts.*

**p95 latency** — 95% of requests were faster than this. Better than an average, which hides
the slow tail.

**Instant vs range query** — one value now, versus a series over time.
*Ours: instant for detection, range for the charts and sparklines.*

**Golden signals** — the four things worth watching: traffic, errors, latency, saturation.
*Ours: request rate, error ratio, p95 latency, connection-pool usage.*

**Error ratio** — failed requests ÷ total requests. The single number detection runs on.
*Ours: **5% sustained over two consecutive 15-second checks** opens an incident. One blip
doesn't. Zero traffic doesn't (0 errors out of 0 requests isn't an outage).*

**Connection pool** — a set of open database connections a service reuses, because opening one
per query is slow.
*Ours: the pool gauges are what let an investigation **prove** connection exhaustion instead of
guessing — `db_pool_waiting` above zero means requests are queued waiting for a connection.*

## 3. Our architecture

**Event sourcing** — instead of only storing current state, you store **every event that ever
happened**, in order. Current state is derivable from replaying them.
*Ours: the `events` table is the spine of the whole system.*

**Event bus** — the channel features use to talk to each other. A feature **emits** an event; other
features **subscribe**. Nobody calls anybody directly.
*Ours: `backend/app/core/events.py`. The detector emits `incident.opened`; the agent had
registered `@events.on("incident.opened")` and wakes up.*

**Why it matters (say this one):** the same table is the **message bus, the incident timeline,
and the audit log**. One table, three jobs. It also means adding Freshservice touches nothing
that already works — it's just one more subscriber.

**Subscriber isolation** — each subscriber runs in its own task, so one crashing can't affect
the others. A failure is recorded as a `handler.failed` event.

**Append-only** — rows can be inserted, never updated or deleted.
*Ours: enforced by database triggers `events_no_update`, `events_no_delete`, `events_no_truncate`.
Try `update public.events …` and it errors.*

**Hash** — a fixed-length fingerprint of some data. Change one character of the input and the
fingerprint changes completely. We use **SHA-256**.

**Hash chain** — each event's hash covers **the previous event's hash plus its own contents**.
So editing any event breaks that event *and every event after it*. That's what "tamper-evident"
means: not that it can't be changed, but that changing it **cannot be hidden**.
*Ours: computed by the `seal_event` database trigger on insert; checked by
`verify_event_chain()`; shown by the green/red badge on `/audit`.*

**Idempotent / one-time claim** — doing something twice has the same effect as doing it once.
*Ours: the executor claims a one-time execution record, so two approvals landing together can't
run the fix twice.*

**Fingerprint (deduplication)** — a key that identifies "the same problem", so one outage
doesn't open fifty incidents.
*Ours: `service:signal`, with a unique constraint so a duplicate insert is silently ignored
while an incident is open.*

**Sweeper** — a loop that catches work that fell through the cracks.
*Ours: the event bus is in-process, so if the backend restarts between approval and execution
the event is lost. A sweeper checks every 30 seconds for approved-but-unexecuted proposals.*

## 4. The AI layer

**LLM (Large Language Model)** — the model. Ours is **Claude Sonnet 5** (`claude-sonnet-5`).

**Tool use / function calling** — the model doesn't run code. It **asks** to call a named tool
with typed arguments; our code runs it and hands back the result; the model continues. That
loop is the investigation.
*Ours: `backend/app/features/investigation/agent.py`.*

**Agent** — an LLM in a loop with tools and a goal, deciding its own next step.
*Ours: 9 read-only tools — metrics, pod logs, pod status, deployment config, Service ports,
rollout history, Postgres settings, dependencies, and a live TCP probe from inside a pod.*

**Read-only tools** — every investigation tool **looks**; none of them **touch**. There is no code
path from the agent to a cluster write.

**Structured output** — forcing the model to answer in a fixed shape rather than prose, so the
program can act on it.

**Evidence-compulsory** — our rule: a finding is **rejected** unless it cites the specific tool
results that prove it. Every claim on the timeline links to the raw output behind it.
*Say this one: the human approving isn't trusting the AI, they're reading its working.*

**Token** — the unit models read and bill in, roughly ¾ of a word.
*Ours: each investigation is logged with its token usage and costs about **$0.05**.*

**Budget / cap** — limits that stop a runaway loop.
*Ours: max 14 tool calls, 120-second time budget, max 3 investigations per incident.*

**Hallucination** — a model stating something confidently that isn't true. The evidence rule and
the typed action catalog are our two defences.

**MCP (Model Context Protocol)** — a standard way for a system to expose its operations as tools
an AI can call, so you don't write a client by hand.
*Ours: Freshworks hosts one at `<domain>.freshservice.com/mcp`. It covers tickets, notes and
solution articles — **but not changes or approvals**, which is why we also use the REST API.*

## 5. Safety and governance

**Governed autonomy** — the AI acts, but only inside limits a human set in advance. Use this
phrase instead of "autonomous", which invites "so it does things without asking?"

**Action catalog** — the AI never writes a command. It picks one of **four** named actions and
fills in typed parameters.
*Ours: `restart_service`, `scale_service` (1–5), `set_service_port`,
`set_database_max_connections` (20–200).*

**Allow-list** — the explicit set of targets an action may touch. Anything not on it is refused.
*Ours: `{order-service, payment-service}` for services, `{postgres}` for network changes.*

**Fails closed** — when something is unclear or missing, the system **refuses** rather than
proceeds. The opposite (fails open) is how accidents happen.

**Policy** — a pure function deciding risk level and how many approvals an action needs.
*Ours: low/medium need 1 approval, high needs 2.*

**Blast radius** — how much is affected if this goes wrong.
*Ours: an action touching 3+ services is automatically treated as high risk.*

**Human in the loop** — a person must approve before anything executes.

**Atomic approval** — the database update only succeeds if the proposal is still `pending`, so
two approvers clicking simultaneously can't double-approve.

**Verify-then-rollback** — after executing, watch for recovery against a PromQL condition for 2
minutes. If it doesn't recover, **undo the change automatically** and hand it back to a human.

**Kill switch** — one control that stops all execution immediately, re-checked by the executor
at execution time, not just at approval time.

**Least privilege** — give an identity the minimum permissions it needs. Our RBAC role is the
example.

**Defence in depth / two fences** — two independent barriers, so one failing doesn't mean a
breach.
*Ours: the **cluster identity** (can't delete or create anything) and the **action catalog**
(can't express a dangerous action in the first place). Either alone would stop a disaster.*

**Audit trail** — the record of who did what, when, and why. Ours is the hash-chained events
table, and it's verifiable rather than merely written down.

## 6. Backend stack

**FastAPI** — the Python web framework serving our API.

**Pydantic** — defines the shape of data and validates it at the boundary. Bad data is rejected
before it reaches any logic.
*Ours: every action's parameters are a Pydantic model — that's what "typed parameters" means.*

**Uvicorn** — the server that actually runs FastAPI.

**async / await** — one process handling many waiting operations at once instead of blocking.
*Ours: matters because we're constantly waiting on Prometheus, Kubernetes and the database.*

**Event loop** — the thing scheduling async work.
*Ours: `run.py` exists because Windows defaults to a loop (ProactorEventLoop) our Postgres driver
can't use, so we start uvicorn on a SelectorEventLoop instead.*

**psycopg** — the Postgres driver. **httpx** — the HTTP client. **PyJWT** — verifies login tokens.

**Connection pooling** (again, ours) — the backend keeps a pool of database connections open.

**REST API** — an HTTP interface where URLs are resources and verbs are GET/POST/PUT/DELETE.
*Ours: `GET /api/v2/changes/{id}/approvals` is how we read a Freshservice approval.*

**Polling** — asking repeatedly on a timer. **Webhook** — the other system calls you when
something happens.
*Ours: polling everywhere, because the laptop is behind a router and nothing can call in.*

**Pytest / ruff** — test runner and linter. *Ours: 81 tests, and markers so database tests
(`-m db`) only run on request, inside a transaction that's rolled back.*

## 7. Frontend stack

**React** — builds the UI from components. **TypeScript** — JavaScript with types checked before
it runs. **Vite** — the dev server and bundler.

**Tailwind CSS** — styling written as utility classes in the markup. **shadcn/ui** — components
copied into your codebase rather than installed, so you own them.

**TanStack Query** — manages server data: fetching, caching, refetching, loading and error
states. *Ours: why panels show "could not load this" instead of spinning forever.*

**Supabase Realtime** — a websocket push so the UI updates without refreshing.
*Ours: `postgres_changes`, one channel per subscriber — sharing a channel name was a real bug
we hit.*

**Recharts** — the charts. **cmdk** — the ⌘K command palette. **sonner** — toasts.
**motion** — animation.

**openapi-typescript** — reads the backend's OpenAPI spec and generates matching TypeScript
types, so the frontend can't drift from the backend.

**Optimistic update** — showing the result before the server confirms.

**Hot module reload (HMR)** — the frontend updates on save. The backend doesn't; restart it.

## 8. Database, auth, identity

**Postgres** — the database. Two separate ones here: the one the **demo services** use (inside
the cluster) and the one **SentinelOps itself** uses (Supabase, in the cloud). Deliberately
separate: *a tool that diagnoses an outage must not be part of the outage.*

**Supabase** — hosted Postgres plus authentication, plus realtime.

**Migration** — a versioned SQL file that changes the schema.
*Ours: `supabase/migrations/0001_init.sql`.*

**Trigger** — code the database runs automatically on insert/update/delete.
*Ours: `seal_event` computes the hash chain; `reject_event_mutation` blocks edits.*

**Transaction / rollback** — a group of statements that either all apply or none do.
*Ours: how the database tests leave nothing behind.*

**Advisory lock** — a lock you take voluntarily to serialise work.
*Ours: so two events inserted at the same instant can't both claim the same place in the chain.*

**Row Level Security (RLS)** — permissions enforced per row by the database itself, not by
application code.

**JWT (JSON Web Token)** — a signed token proving who you are. **ES256** is the signing
algorithm; **JWKS** is the public-key set used to verify it.
*Ours: 90 seconds of clock-skew leeway, because the laptop clock drifting 9 seconds behind
Supabase made every login fail.*

**Role** (ours) — viewer, responder, approver, admin. Only approver and admin can approve.

**Environment variable / `.env`** — configuration and secrets kept out of the code.
*Ours: gitignored. `.env.example` is committed and holds no real values.*

## 9. ITSM and Freshservice

**ITSM (IT Service Management)** — how organisations run IT as a service: tickets, changes,
problems, approvals. **ITIL** is the framework most of it comes from.

**Incident** (ITIL) — "something is broken right now."
**Problem** (ITIL) — "why does this keep happening." Most teams never write the problem record
because the fire is out. *Ours drafts it automatically while the evidence is fresh.*

**Change request** — a proposed alteration to production that someone must approve.
*Ours: every proposed fix becomes one. **This is the centre of our pitch** — the approval lives
in the customer's real change process, not in our dashboard.*

**Normal vs Emergency change** — routine and pre-reviewed, versus urgent with a faster path.
*Ours: chosen by the policy's risk level.*

**CAB (Change Advisory Board)** — the group that approves changes. Worth knowing the acronym.

**Solution articles** — Freshservice's knowledge base; a company's own written runbooks.
*Ours: an agent tool, so the company's own documentation becomes evidence the AI can cite.*

**Freshservice vs Freshdesk** — Freshservice is ITSM (internal IT). Freshdesk is customer
support. We use **Freshservice**.

**Agent** (Freshservice sense) — a staff user. Note the collision with "AI agent"; be explicit
about which you mean.

## 10. The category and the market

**SRE (Site Reliability Engineering)** — running production systems as an engineering problem.

**On-call** — whoever gets paged at 3am. **MTTR (Mean Time To Recovery)** — the headline metric:
how long from breaking to fixed.

**AIOps** — the older category: machine learning over alerts, mostly correlation and noise
reduction.

**AI SRE** — the current category. **Gartner published its first Market Guide in January 2026.**
Competitors include Resolve AI (**$125M Series A at $1B, February 2026**), NeuBird, incident.io,
Rootly, Ciroos, plus Datadog, Dynatrace and PagerDuty.

**The line to remember:** the market's own summary is that *autonomous investigation is real and
reliable; autonomous remediation is mostly still supervised.* That gap is exactly what we built
into — and we're not claiming better AI, we're claiming the governance that makes acting safe.

**Runbook** — written instructions for handling a known failure.

**Postmortem** — the write-up after an incident: what happened, why, what changes.

**Blameless** — the convention that postmortems name causes, not people.
